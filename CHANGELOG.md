# Changelog

All notable changes to `exiftool-rs` are documented here.

## [1.0.0] - unreleased

exiftool-rs becomes a faithful port of Perl ExifTool 13.60: ExifTool's own
modules, embedded, run by a Perl interpreter written in Rust, with its subs
and the `exiftool` application ported to Rust one by one. It replaces the
0.x reimplementation (MIGRATION.md).

### Changed

- Everything read, printed and written is ExifTool's: ExifTool's test suite
  passes unchanged (114 scripts, 604 tests), every test image extracts as
  Perl does, and the CLI is compared with Perl's `exiftool` case by case.
- The CLI has every option of the `exiftool` application.
- The Rust API keeps 0.14's names and signatures, as a facade over
  Image::ExifTool (docs/port/API.md lists the differences).
- 0.x's writers for the types ExifTool does not write (ID3, FLAC, Ogg,
  Opus, Matroska) are kept, behind the `extra-writers` feature (default).
- Building needs a C compiler (PCRE2 and zlib are built in).

### Removed

- The internal modules 0.x exported (`formats`, `metadata`, `tags`,
  `writer`, `encoding`, `geolocation`, `geotag`, `i18n`, `md5`...).

## [0.14.1] - 2026-10-24

Twelve reports from @julyx10, each checked against ExifTool 13.59 on the
synthetic files of the report (kept as regression tests in `tests/issues/`).

### Added

- EXIF writing covers every writable tag of Exif.pm and GPS.pm whose inverse
  conversion is ported, 338 of 370, from a table generated by
  `scripts/gen_exif_write.pl`. It used to know 29 tags, so ExposureTime,
  FNumber, ISO, FocalLength and most capture settings could not be written
  or copied (#36).
- QuickTime: GPS from `location.ISO6709`, UserData and ItemList `©xyz`, with
  Composite GPSLatitude, GPSLongitude, GPSAltitude and GPSAltitudeRef (#26).
- OpenEXR: every attribute of OpenEXR::Main (capture date, ISO, exposure,
  focus distance, GPS, ...), and Perl's generated names for the others (#33).
- XMP: ExifTool's table of namespace URIs and its fixes for wrong ones, with
  the `[minor] Fixed incorrect URI` warning (#32).

### Changed

- Low-level writer API: `writer::exif_edit::TagSpec` has a new `info` field,
  its row of the generated write table. The high-level API (`ExifTool`,
  `Options`, `Tag`) is unchanged.

### Fixed

- `set_new_values_from_file` copies like SetNewValuesFromFile: the source is
  read with duplicates (a composite hid EXIF:GPSLatitude, so the
  coordinates were lost), protected tags and the ExifTool group are left
  unless named (#36).
- XMP GPS coordinates such as `12,30N` are converted, in print and `-n`
  modes (#25).
- QuickTime: zero dates print as `0000:00:00 00:00:00`, MediaLanguageCode
  0x7fff is kept, PixelAspectRatio is read, unknown Keys are named as
  ExifTool names them (#26).
- XPKeywords and the other XP tags are decoded as UTF-16 text (#27).
- Samsung Type2 maker notes: the hand-written table had wrong IDs (0xa001 is
  FirmwareName, 0xa002 SerialNumber, 0xa003 LensType, and ten more), and a
  maker note tag no longer hides an EXIF tag stored after it, such as
  ExifIFD:LensModel (#28).
- Canon CRW: FocalLength is divided by FocalUnits (#29), Composite ISO uses
  the ShotInfo BaseISO (#30), and Min/MaxFocalLength, Lens, Lens35efl and the
  LensID fallback are in millimetres (#35). DriveMode and ShootingMode are
  computed for CRW too, and values missing from a Canon lookup print as
  `Unknown (N)`.
- UserComment without a character code keeps all its text and gets the
  `Invalid EXIF text encoding` warning, as ConvertExifText does (#31).
- EXIF values missing from a tag's PrintConv print as `Unknown (N)` instead
  of the entry another module has for a tag of the same name: Orientation 0
  was "Horizontal (normal)" (#34). Compression, Flash, ColorSpace,
  MeteringMode and the other EXIF enums had the same bug.

## [0.14.0] - 2026-10-23

### Added

- `ExifTool::write_warnings()`: the warnings of the last `write_info` call,
  one per queued request that did not take effect (a tag ExifTool does not
  define, one the file type cannot hold, or one our writer does not handle).
  The CLI prints them as `Warning: ...` lines, as ExifTool prints
  "Tag 'X' is not defined".

### Changed

- A request that does not take effect no longer fails the whole write when
  it is the only one (#22 follow-up). As ExifTool 13.59 does (`-Foo=bar`, or
  `-PNG:XMLcomadobexmp=` on the `XML:com.adobe.xmp` iTXt chunk with a
  language code: "Warning: Tag ... is not defined", "1 image files copied"),
  `write_info` to a new destination writes an unchanged copy and returns
  `Ok(0)`, with the skipped requests in `write_warnings()`. In place, it
  still fails and leaves the file alone (ExifTool's "Nothing to do."). Mixed
  with requests that do apply, those are written and counted, as before.

## [0.13.0] - 2026-10-19

PNG writing brought in line with ExifTool 13.59, chunk by chunk (#22).

### Changed

- **Breaking (low-level writer API):** `writer::png_writer::PngTextChanges`
  has three new fields, `delete_icc_profile`, `delete_physical_pixel` and
  `delete_everything`; a struct literal needs them (or `..Default::default()`).

### Performance

- JPEG trailers are found the way ExifTool's ProcessTrailers finds them,
  walking back from the end of the file, instead of scanning the whole image
  for each trailer signature: about 10× faster on a corpus of camera JPEGs.
  Composite tags avoid repeated lookups and clones, Deflate goes through
  `flate2`, and Google HDR+ maker notes parse about 5× faster (#23, thanks
  @jmoiron).

### Fixed

- GPS composites and tags match ExifTool in numeric mode (`-n`) and on
  unknown values (#23): `GPSLatitude`/`GPSLongitude` are signed decimal
  degrees, `GPSPosition` is the two numbers, `GPSAltitude` is signed metres,
  `GPSDateTime` is built from the unrounded time stamp, and an unknown
  `GPSLatitudeRef`-style value prints as `Unknown (x)` instead of vanishing.

- Olympus ORF files are read again (#24). ORF swaps the TIFF magic 42 for
  0x4F52 (`IIRO`, `MMOR`) or 0x5352 (`IIRS`); detection never looked at
  those headers and the TIFF reader rejected them, so every ORF came back as
  `UnsupportedFileType`. Both now accept them, as ExifTool does.

- `PNG:all` deletes what ExifTool deletes: every textual tag, the tIME
  (`ModifyDate`), gAMA (`Gamma`) and sRGB (`SRGBRendering`) chunks, and a
  text chunk whose `XML:com.adobe.xmp` keyword carries a language code (read
  as `PNG:XMLcomadobexmp`, an ordinary text tag for ExifTool). It keeps the
  XMP packet, the raw profiles, iCCP, pHYs and the image data, byte for byte.
  A tag deleted with the group and also written comes back as a new chunk.
  It used to fail with "none of the requested changes could be written",
  because the image header tags the PNG group also names were still there.
- `PNG:ModifyDate`, `PNG:Gamma` and `PNG:SRGBRendering` are written and
  deleted in their own chunks (tIME, gAMA, sRGB), with ExifTool's
  conversions; they used to become tEXt chunks of those names. New gAMA and
  sRGB chunks go before PLTE.
- The `XML:com.adobe.xmp` keyword is the XMP packet in tEXt and zTXt chunks
  too, and in a compressed iTXt chunk: `XMP:all` deletes it, an XMP edit
  rewrites it as an uncompressed iTXt chunk (it used to add a second packet,
  or fail on a compressed one).
- `all` also deletes iCCP, pHYs, the SEAL chunk, every raw profile and the
  data after IEND; `EXIF:all` deletes `Raw profile type exif`, `XMP:all`
  `Raw profile type xmp`. `ICC_Profile:all` and `PNG-pHYs:all` delete iCCP
  and pHYs.
- A text tag is matched through ExifTool's tag names (`CreationTime` is the
  `Creation Time` keyword, `Description-fr` the French iTXt chunk, which
  `PNG:Description` no longer deletes), and a new one gets its keyword.
- Reading: zTXt chunks, compressed iTXt chunks, gAMA (`Gamma`), iCCP
  (`ProfileName` and the ICC profile), raw profiles (as EXIF, XMP or ICC),
  language-specific text tags (`Description-fr`), and ExifTool's names for
  the `Software`, `Warning` (`PNGWarning`) and unknown keywords.

## [0.12.0] - 2026-10-17

### Changed

- **Breaking:** `write_info` counts only the requests that changed the file.
  Deleting a tag the file does not have used to count as done; it now counts
  as nothing, the way ExifTool reports "1 image files unchanged": the call
  returns `Ok(0)`, is not an error, and still writes the output. Writing a
  value still counts even when the tag already had it, as in ExifTool (#21).

## [0.11.0] - 2026-10-17

Parity work under `-j -a -G0:1:4 -n -struct -b -u -U`, the flags the
dng-compare project extracts with, measured against Perl ExifTool 13.59
(#20, by Alexy Khrabrov).

### Added

- `-struct` (`Options::struct_output`): structured XMP output. A property
  whose value is a structure, or a list holding one, becomes one tag with a
  `Value::Struct` (or a list of them) instead of its flattened fields; every
  list-valued XMP tag is reported as a list even with one item; language
  alternatives inside structures expand to `Field` and `Field-lang`; fields
  from a foreign namespace in an open structure are qualified
  (`XMP-exif:Flash`). Implemented as a tree pass (`metadata::xmp_struct`)
  over the packet that re-reads it without the structure roots, so the
  streaming reader and its flat-name overrides stay untouched. Composites
  still see the replaced flattened fields (`Composite:Flash`).
- `Value::Struct` with ExifTool's text serialisation (`{Key=Value,List=[a,b]}`).
- `-G0:1:4` and any other family combination: labels joined by `:`, a name
  equal to the previous one dropped (`File:FileType`), family 4 as ExifTool's
  `CopyN` instance number.
- `-b` together with `-j` emits binary values as `base64:` strings instead of
  switching to the raw binary dump.
- `-n` is honoured by `-j` output (JSON used to print PrintConv values).
- `tests/dng_compare_parity.rs`: synthetic DNG and Lightroom-style XMP
  fixtures checked against Perl 13.59 values.

### Changed

- Breaking: `Value` has a new variant, `Value::Struct`, so an exhaustive
  `match` on it needs an arm for it.
- Breaking, once: `Value`, `Error` and `FileType` are now
  `#[non_exhaustive]`. A `match` on them needs a `_` arm, and in exchange a
  future variant (a new value kind, error or file format) no longer breaks
  anyone's build, so it can ship in a patch release.

### Fixed

- `write_info` no longer overwrites a file that happens to be named like its
  temporary file, and no longer leaves its temporary file behind when the
  final rename fails (#19). The temporary file now gets a fresh name, created
  exclusively next to the destination, and is removed on any failure. A
  rewritten file keeps its permissions.
- A top-level `rdf:Description` named by `rdf:nodeID` and referenced nowhere
  had every list in it read twice (`Ann, Ann, Bob`); it is now read like any
  other Description.
- Numeric (`-n`) values of the pseudo tags: `FileType` is the short code
  (`DNG`, not the enum name `Dng`); `FileTypeExtension` is upper-case raw and
  lower-case print; `ExifByteOrder` and `MakerNoteByteOrder` are `II`/`MM`
  raw; `Directory` is `.` for a bare file name; `ImageSize` is `W H` raw and
  `WxH` print.
- Equal repeated items of a flattened XMP list field were collapsed to one
  (`What: "Correction"` for two masks); every occurrence is kept.
- ValueConv under `-n` for undefined-typed EXIF tags (`ExifVersion`,
  `FlashpixVersion`, `InteropVersion`, `FileSource`, `SceneType`,
  `ComponentsConfiguration`), XMP dates, PLUS vocabulary codes and rational
  lists (`aux:LensInfo`).

### Known gaps

- Many composites and MakerNotes still carry PrintConv text as their raw
  value under `-n`; `-U` unknown MakerNote tags are far less complete than
  Perl; `CopyN` follows discovery order rather than ExifTool's priority
  displacement; blank-node (`rdf:nodeID`) structures are not rebuilt.

## [0.10.0] - 2026-10-16

### Changed

- Breaking: the format writers in `writer` (TIFF, PNG, GIF, PDF, PSD, WebP,
  JP2/JXL and others) take new arguments, and a raw value such as
  `ColorSpace=2` for a conversion with no fallback is now rejected, as
  ExifTool rejects it.
- Dependencies updated; the GUI uses egui and eframe 0.37.

### Fixed

- HEIF, HEIC and AVIF files can now really be written (#17). The writer used
  to hand them to the MP4 writer, which rewrites `moov` and skips deletions,
  while a HEIF keeps its EXIF and XMP as items of the `meta` box: every edit
  was dropped and `write_info` still reported each request as written. The
  new writer edits the primary image's Exif and XMP items the way ExifTool's
  `WriteItemInfo` does. It sets, adds and deletes single tags, deletes whole
  groups (`EXIF:all`, `XMP:all`, `GPS:all`, `ExifIFD:all`, `XMP-dc:all`,
  `all`), creates a missing Exif or XMP item, and relocates every other item
  in `iloc` (field sizes 0, 4 and 8, base offsets, several extents, versions
  0 to 2, data in `mdat` or `idat`) along with the chunk offsets of any
  track. The coded image and its properties are copied byte for byte.
  Against ExifTool 13.59, the reporter's 16 deletions, `-EXIF:all=
  -XMP:all=`, `-GPS:all=`, edits of Make, Artist and the GPS position, and
  adding EXIF, GPS or XMP to a file without them give the same tags and
  values on the reporter's file and on AVIF samples; libheif decodes every
  output to the same pixels.
  Differences from ExifTool: an item whose metadata is all deleted is
  removed (ExifTool keeps it, empty), and deleted bytes are zeroed;
  `XMP-x:XMPToolkit` names exiftool-rs; ExifTool's 2 KB of XMP padding is
  not added.
- Reading HEIF/AVIF now extracts the Exif and XMP items (it extracted
  neither) and the `colr`, `pixi` and `clap` item properties
  (ColorProfiles, ColorPrimaries, ..., ImagePixelDepth, CleanAperture); a
  file whose major brand is `heic` is typed HEIC (`image/heic`), as
  ExifTool types it. XMP GPS coordinates print as ExifTool prints them
  (`51 deg 30' 2.52" N`, not `51,30.042N`), and the XMP Composite
  GPSLatitudeRef/GPSLongitudeRef are built. The reporter's file and the two
  new AVIF samples now read identically to ExifTool 13.59.
- `write_info` returns the number of requests that took effect, checked by
  reading the output back: a written tag must be there with its value, a
  deleted tag or group must be gone. It used to return the number of queued
  requests whatever happened. When none of them can be applied to the file
  type, it now fails and writes nothing.
- `EXIF:all` and `XMP:all` delete the group in JPEG and WebP too; only the
  `EXIF:*` spelling did.
- Writing an XMP sidecar edits the packet in place instead of replacing it
  with the written properties alone, so the rest of the file survives.
- Every write now really lands, checked end to end by the parity audit's
  write matrix: 418 of 460 cases are identical to ExifTool 13.59, up from
  29, with no silent no-op, refused write or broken file left (114 silent
  no-ops and 64 broken files before). The other 37 cases have no Perl
  reference (ExifTool does not write ID3, Vorbis comments or Matroska, and
  refuses the truncated NEF/ARW samples) and are checked by re-reading
  alone. 5 known mismatches remain, all on files damaged at the source:
  GE.jpg, whose bogus maker-note offsets ExifTool repairs by rebuilding the
  maker note while we keep it as it is, and a Ricoh.jpg value that points at
  layout-dependent bytes.
- JPEG: EXIF is edited in place instead of rebuilt, keeping the byte order,
  IFD1 and its thumbnail, the Interop IFD and valid maker-note offsets
  (Perl used to warn "Invalid PrintIM header" or "Bad ExifIFD directory" on
  our output). GPS tags are written, `GPS:all` deletes the GPS IFD, an
  unqualified delete only reaches the tag's write group, and a new EXIF
  block takes its resolution from JFIF, as ExifTool does. AFCP and MPF
  offsets follow any change in size.
- IPTC: the encoder is a port of ExifTool's `DoWriteIPTC`, so the record
  bytes and the digest match ExifTool's. Only the IPTC resource of the
  Photoshop block is edited; the other resources and IPTCDigest were lost.
  Times without a zone use the local zone and "Latin" text is cp1252, as in
  ExifTool. IPTC in AFCP, FotoStation, PhotoMechanic and MIE trailers is
  edited along the whole trailer chain.
- XMP: packets are edited in place everywhere (including UTF-16 packets and
  extended XMP, which is merged and removed with `XMP:all`), and each tag
  goes to the namespace ExifTool picks, from a table generated from its
  sources (`XMP:Description` went to `xmp` instead of `dc`). The inverse
  conversions of the XMP tables are ported, so the 54 tags we refused are
  written. An ungrouped tag is created in its preferred family and replaced
  wherever another family already holds it, as `SetNewValue` does.
- TIFF and TIFF-based RAW (DNG, CR2, NEF, ARW) can add and delete tags, not
  only replace existing ones; image data stays at its offsets.
- PNG text chunks are replaced instead of duplicated and can be deleted;
  EXIF and XMP go to their own chunks. GIF comments are found by walking
  the block structure. PDF edits are written as an incremental update, as
  ExifTool does, instead of splicing bytes and breaking the xref table.
  PSD, WebP, JP2 and JXL edit their existing EXIF, IPTC and XMP instead of
  rebuilding them from the new values alone.
- QuickTime (MOV, MP4, M4A): deletions are applied, other ItemList tags
  are kept, UserData and Keys are edited, XMP goes where ExifTool reads it,
  and `stco`/`co64` chunk offsets are relocated. ID3 frames are edited in
  place (v2.2 to 2.4, ID3v1 kept in sync, AIFF `ID3 ` chunk); FLAC and
  Ogg (Vorbis, Opus, FLAC) comments are edited, re-paged and re-checksummed;
  Matroska writes its title and tags and keeps its index consistent.
- Reading: maker-note tables are chosen as ExifTool chooses them once Make,
  Model or Software are changed or deleted (they come from IFD0 only, and a
  missing value reads as empty), with Canon, Nikon, Pentax, Ricoh and Sony
  model conditions ported. MIE trailer directories are decoded, PDF
  reading uses the last revision, and empty ID3v1 fields read as ExifTool
  reads them.

### Added

- The parity audit now checks writes end to end, and the
  [parity report](https://le-syl21.github.io/exiftool-rs/#write) has a Write
  section. Every corpus file whose type exiftool-rs writes gets a small,
  deterministic set of edits (set, add and delete a tag, delete a whole
  EXIF, GPS, XMP or IPTC group, and a mixed edit), applied both with
  `write_info` and with Perl ExifTool. Both outputs are re-read by Perl
  ExifTool and by exiftool-rs, and each case checks the requested state,
  equality with Perl's output, agreement between the two readers, and that
  the file still reads without a new error or warning. `write_info`
  returning `Ok` with nothing changed, the pattern of issue #17, is
  reported as a silent no-op. Known failures are recorded in
  `tests/parity_write_baseline.txt`, and the release gate fails on a new
  one. `parity --dump` emits the write results after the read TSV, and
  `--dump-write` emits them alone. The four IPTC write cases the audit
  had before are part of the matrix, now compared on every tag rather than
  on the IPTC block alone.
- `writer::exif_edit` edits an EXIF block in place, keeping what it is not
  asked to change (IFD1, Interop IFD, maker notes and their offsets), and
  follows ExifTool's mandatory-tag rules: a directory left with only its
  mandatory tags after a deletion is dropped, and a new one gets them.
- `writer::xmp_edit` edits an XMP packet in place.
- `formats::heif_items` parses the HEIF item tables (`iinf`, `iloc`, `iref`,
  `ipma`, `idat`).
- A `write_heif` fuzz target.

## [0.9.0] - 2026-10-01

Faster to build and smaller, with no tag, value or group change on valid
files: the parity audit still reads 196 / 196 files identical to ExifTool
13.59. Six more fuzzing rounds (about seven hours over every supported
extension) found the cases listed under Fixed.

### Changed

- A release build of the crate takes about a third of the time it did, and
  the released Linux CLI is 40 % smaller (#13). Three generated modules — the
  print conversions, the 283 binary sub-tables and Sony's 59 ciphered
  tables — unrolled every table into code of its own, and that code was
  most of the build and of the binary. Their generators now write the
  tables as static data, read by a few lookup functions and two
  hand-written interpreters (`tags::binary_tables`,
  `tags::sony_ciphered`). Nothing moved behind a feature flag, and the
  output does not change: a dump of the test and fuzz corpora under 25
  option sets and 15 CLI modes, plus about ten million direct calls into
  the generated tables, is byte-identical before and after, and the parity
  audit still reads 196 / 196. Measured on an i7-8700K with `-j 2`, 0.8.2
  against this tree (CPU is user + system):

  | | 0.8.2 | Now |
  |---|---|---|
  | Release build of the library and CLI, wall / CPU | 180 s / 304 s | 59 s / 105 s |
  | The library built as a dependency (Cargo's default release profile), wall / CPU | 180 s / 294 s | 56 s / 91 s |
  | Debug build of the library and CLI, wall / CPU | 24 s / 31 s | 14 s / 19 s |
  | Peak memory of the release build | 2.56 GiB | 1.37 GiB |
  | LLVM IR of the library (`cargo llvm-lines`) | 3.43 M lines | 1.39 M lines |
  | CLI binary, Linux x86-64, as released | 27.1 MB | 16.4 MB |

  Of the 10.7 MB the binary loses, 6.2 MB is this change and 4.6 MB the
  stripped symbol table below.
- Release builds strip the symbol table (`strip = true`), about a fifth of
  the binary. A panic still gives its file and line; backtraces lose their
  function names. The profile applies to builds of this repository only: a
  crate that depends on this one keeps its own.
- CI builds the tests with LTO off. Under thin LTO every test executable
  repeated the library's whole optimisation at its own link; building them
  takes 50 s instead of 336 s on the machine above. The binaries CI ships
  are still built with thin LTO.

- The published crate no longer carries `tests/`: Cargo never builds a
  dependency's tests, and ours need `tests/images/`, which was already left
  out. The download loses about 800 files.
- Dependencies: brotli 9 (JPEG XL / JPEG 2000 brotli boxes), egui and
  eframe 0.36.2 (GUI only), thiserror 2.0.21, encoding_rs 0.8.42. The
  lockfile's encoding_rs needs Rust 1.88; a crate depending on this one
  resolves its own.

### Fixed

- PLIST (binary and XML) and XMP GContainer tags came out in a different
  order from one run to the next. They now follow the document, as in
  ExifTool.

Corrupt or hostile files could still panic, allocate gigabytes or take
seconds per kilobyte. Each case now returns, with a regression input under
`tests/malformed/`:

- EXIF: an IFD0 SubIFDs list pointing back into IFD0 re-read it once per
  entry (110 KB in, 42 MB of tags and 1 GB of memory out). ExifTool skips
  such an offset as suspicious, and follows at most ten SubIFDs; both rules
  are now applied, with ExifTool's warnings.
- Composite ThumbnailTIFF: the strip was padded to the declared
  StripByteCounts, so a 6 KB NEF asked for 4 GB. ExifTool drops the
  composite when the strip is not in the file; a strip longer than the
  file never is.
- QuickTime: a constant-size `stsz` expanded its declared sample count
  (up to 16 GB).
- Dates in MRC, QuickTime, gzip, AIFF and FLV were found by walking one
  year at a time; a timestamp billions of years away hung the reader. Whole
  400-year cycles are now skipped first, which gives the same dates.
- JSON: nested arrays were copied at every level (quadratic on unmatched
  `[`); arrays deeper than 64 levels are skipped.
- XMP: flattening a long struct field name was quadratic (1.4 s for 60 KB);
  the output is unchanged.
- Allocations and bounds tests that could overflow on sizes read from the
  file: binary plist offset tables (also in macOS `._` sidecars), CZI
  metadata offsets, BigTIFF value offsets, RealMedia RJMD sub-directories,
  MRC OLE dates.
- Text sliced inside a multi-byte character: PostScript comments, Internet
  shortcut (`.URL`) dates, plist dates, RED dates and times.

## [0.8.2] - 2026-09-26

A fifth fuzzing round, run before 0.8.1 reached crates.io, found three more
cases. 0.8.1 was published on GitHub only; this release supersedes it. The
parity audit still reads 196 / 196 files identical to ExifTool 13.59.

### Fixed

- CRW (Canon RAW): sibling entries pointing at the same sub-directory were
  read again at every level, so a 54 KB file grew past 2 GB of tags. A
  directory is now read once, as ExifTool's `PROCESSED` check does.
- PDF: an octal escape above `\377` in a string overflowed a byte; the high
  bit is dropped, as the PDF specification says.

## [0.8.1] - 2026-09-25

A robustness release. No tag, value or group changes: the parity audit still
reads 196 / 196 files identical to ExifTool 13.59.

### Fixed

Corrupt, truncated or hostile files could abort the process (stack overflow),
panic, allocate gigabytes or loop forever. Found by fuzzing every supported
extension (`fuzz/`), each case now returns partial tags or an error:

- EXIF: a SubIFD or ExifIFD pointer back to an IFD already being read
  recursed until the stack overflowed. IFD nesting is capped at 32 and no IFD
  is read twice.
- Lytro (`.lfp`): the JSON reader looped forever on a stray character inside
  an array, and slowed quadratically on deep nesting (now capped at 64).
- JPEG extended XMP: the buffer was sized from the total the segment
  declares, so a 1 KB file could ask for 3 GB.
- FlashPix / OLE2 (`.fpx`, `.ppt`, `.doc`, ...): cyclic sector chains copied
  up to 655 MB per stream; oversized sector shifts overflowed.
- TNEF: a multi-value property declaring billions of empty values spun.
- Sony SR2: a value count was reserved before checking it fits.
- Binary plist reference cycles; RIFF, DSS and PostScript truncation (the
  four readers fixed first, in `196ebb2`).
- Text cut inside a UTF-8 character: vCard/iCalendar dates, HTML dates,
  GeoTIFF ASCII parameters, composite SubSec dates, RIFF dates, GoPro GPSU
  time, SVG `rdf:RDF` blocks.
- Arithmetic overflow in PICT and PCX dimensions (now signed, as in

## [0.8.0] - 2026-08-29

Three numbers this release is measured by, each printed by a tool in the
repository so none of them rests on anyone's word:

- `conv_coverage` — **4706 / 4706** PrintConv/ValueConv occurrences in
  ExifTool 13.59 are understood by `tags::conv_expr`, 988 / 988 distinct.
- `coverage_report.pl` — **316 / 316** binary sub-tables a reader can get to
  are reached. The 317th is a duplicate ExifTool defines and never points at.
- The four parity baselines under `tests/` are at **zero** deltas.

Both counters run at every tag and block the release if they slip.

### Added

- `tags::conv_expr`, an evaluator for ExifTool's conversion expressions.
  Conversions are carried over from the Perl verbatim and evaluated, rather
  than transcribed by hand, so they cannot drift from their source. It covers
  ExifTool's named helpers, `=~` and `s///`, `my` variables, list operators,
  `map`/`grep`, statement modifiers, `pack`/`unpack`, `sprintf`, and a
  file-level parse state for the conversions that read one.
- `scripts/gen_binary_tables.pl`, a maker-agnostic generator for ExifTool's
  binary sub-tables — **283 tables, 4782 fields**, keyed `Module::Table`. It
  replaced roughly 1700 lines of hand-written decoders with no change in
  output, and reads hundreds of tags that were not read before: Canon's
  ColorData 5 to 12, CameraInfo and ShotInfo; Nikon's thirty-one ShotInfo
  layouts and the twelve custom-settings tables inside them; every remaining
  FLIR record; Panasonic, Kodak, Reconyx, Casio, Minolta, Olympus, Samsung,
  Sanyo, H264, QuickTime and the rest.
- `tags::lens_id` — `XMP::PrintLensID` with `Exif::PrintLensID`,
  `Canon::PrintLensID` and their helpers, against lens tables generated whole:
  the fractional keys `4.1`, `4.2` are what makes narrowing a shared LensID
  possible at all. Checked case for case against Perl over 2866 generated
  cases.
- Sony's enciphered MakerNote sub-tables, generated from Sony.pm.

### Fixed

- Perl's comma binds tighter than `and`, so both halves of `A and B, C` belong
  to the branch. Read as two statements, a data rate of 206 kB/s printed as
  206 MB/s.
- An assignment in a branch Perl never reached must not write back, which was
  the same fault the substitutions already had.
- A conversion found by NAME is a guess: a maker-note tag that shares a name
  with an EXIF one need not share its meaning. Sony's Contrast is a plain
  number where EXIF's is Normal/Soft/Hard.
- A binary-data tag is addressed by its offset, and that offset is the id
  ExifTool reports. Naming them instead collapsed pairs ExifTool keeps apart.
- `rational32` is four bytes — two 16-bit halves — not the eight of the
  `rational64` EXIF writes. Read as eight, 1/20 came out as 1/271.

### Changed

- `coverage_report.pl` counts a table as reached only where a reader can
  actually get to it. It used to match the table's name as a bare substring
  over the whole tree, so any table whose name is an ordinary word counted
  although nothing decoded it.
- `conv_coverage` and `coverage_report.pl` both take `--check`, which turns
  the report into a gate, and both run in CI at every tag.
- CI no longer builds on a push to `main`, and the parity workflow no longer
  runs on a schedule. Work lands directly on `main`, so a build per commit was
  noise, and a scheduled parity run re-measured inputs that are all pinned in
  the repository. The gates run on pull requests, at a tag before anything is
  signed or published, and on demand — which is where parity is now useful,
  pointed at a *newer* ExifTool to price a version bump. 0.7.6 said parity ran
  on pushes to `main`; that was true of 0.7.6 and is no longer.

## [0.7.3] - 2026-07-28

### Added

- `exiftool_rs::EXIFTOOL_VERSION` — the Perl ExifTool release this crate mirrors
  (currently 13.59), as a single source of truth.
- Live parity auditor (`parity` binary, dev-only behind the `parity` feature):
  pins and downloads an ExifTool release, then diffs its output against
  exiftool-rs over a corpus — read parity with a ratcheting baseline, and live
  write-parity by IPTC digest. Complements (and regenerates) the test baselines.
- Published parity report at <https://le-syl21.github.io/exiftool-rs/> — every
  tag exiftool-rs extracts from the shipped corpus, diffed tag-by-tag against
  Perl ExifTool 13.59, regenerated by CI on every push (GitHub Pages).

### Fixed

- **Accented strings are readable (PSP, RealAudio).** The PSP creator-block and
  RealAudio `Copyright` fields were decoded with `from_utf8_lossy`, turning a
  Latin-1 `©`/`ü` into `�`. They now decode UTF-8-or-Latin-1 like the other
  string fields, and the PSP `Copyright` group matches ExifTool (IFD0 wins by
  default). Live read parity against ExifTool 13.59 is now **195/195 files** —
  full data parity. (The `parity` binary's Perl reader was also taught to decode
  ExifTool's raw Latin-1 output faithfully, and now prints an ISO comparison
  table for the read deltas and write cases.)
- **String output matches ExifTool's display sanitization.** Control characters
  (0x01–0x1F, 0x7F) are rendered as `.`, NULs are dropped, and *trailing*
  whitespace is trimmed (leading whitespace is preserved) — exactly as ExifTool's
  console output does (accented/multibyte text is untouched). This alone moved live read parity against ExifTool 13.59 from
  145/195 to 194/195 files byte-identical (the PSP/RealAudio fix above closes the
  rest, reaching 195/195).
- **IPTC write is no longer destructive (JPEG).** Setting one IPTC tag used to
  drop every other IPTC tag in the file (e.g. 20 tags → 1). Writes now merge
  into the file's existing IPTC — updating or deleting the changed datasets in
  place, preserving the rest (including `CodedCharacterSet`) — matching
  ExifTool byte-for-byte (`CurrentIPTCDigest` identical for set / delete / add).
  The PSD writer still replaces; tracked in
  [#7](https://github.com/Le-Syl21/exiftool-rs/issues/7).

## [0.6.1] - 2026-06-14

### Performance

- **Memory-mapped reads.** Files are now `mmap`-ed instead of being read fully
  into memory. The container readers walk by offset (MP4/MOV skip `mdat`,
  Matroska stops at the first `Cluster`, Android MP4s keep `moov` at the end), so
  only the header pages are faulted in. A multi-gigabyte video is parsed by
  touching a few MB rather than allocating and reading the whole file: a real
  2 GB MP4 now parses in ~0 ms with ~9 MB RSS (was a multi-minute stall on very
  large files). Falls back to a plain read when mapping is unavailable. (#5)

### Added

- **QuickTime Keys metadata**: Android device info `AndroidMake`, `AndroidModel`,
  `AndroidVersion` (and other mapped `keys`/`ilst` entries), with QuickTime-style
  `meta` (no version/flags) detection. (#5)
- **Color representation** (`colr` atom): `ColorProfiles`, `ColorPrimaries`,
  `TransferCharacteristics`, `MatrixCoefficients`, `VideoFullRangeFlag`.
- **PreviewImage / ThumbnailImage** from QuickTime `mcvr`/`snal`/`tnal` atoms.

### Fixed

- **Rotation**: the per-track `tkhd` matrix was read 4 bytes early (zeroing the
  rotation sub-matrix); now read at the correct offset and computed via an exact
  port of ExifTool's `GetRotationAngle`. `MatrixStructure` is now emitted per
  track.
- **FilePermissions**: emit the ls-style `-rw-rw-r--` string (with the full octal
  mode as the `-n` value) instead of bare `664`.
- **File dates**: `FileModifyDate`/`FileAccessDate`/`FileInodeChangeDate` now use
  local time with a numeric timezone offset, matching `ConvertUnixTime($val,1)`.
- **FileSize**: raw value stored without 32-bit truncation (files > 4 GB).
- **QuickTime duplicate-tag priority**: `mdhd`/`hdlr` tags follow last-wins while
  `tkhd` tags are Priority-0 (first-wins), matching ExifTool's `FoundTag` rule —
  correct primary `HandlerType`/`MediaDuration`/etc. on multi-track files.

### Test corpus

- Added `tests/images/Android.mp4` (sample from #5) with `.tags`/`.vals` oracles;
  0 name and 0 value deltas vs ExifTool 13.53.
